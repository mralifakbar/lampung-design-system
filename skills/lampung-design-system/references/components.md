# Components

This file is generated by `scripts/build-docs.mjs` from `docs/spec/*.mjs`. Edit the spec, never this file. The same specs build the documentation site (`docs/components/<slug>.html`, one page per component), so what you read here is what people see.

## Reuse before you build

The system already covers almost every need. A page that looks hand-made next to the rest of the product almost always means someone skipped this list. In order:

1. **Find the need in the catalog below.** Each row says when to use the component. Read its file (`components/<slug>.md`) before writing markup: it has the markup, the variants, the states, the motion and what to use instead.
2. **Use the markup as written.** Class names, ARIA attributes and `data-lds-*` hooks are the contract. Change content, not structure.
3. **Combine, do not restyle.** Page layout comes from the layout primitives (`stack`, `cluster`, `auto-grid`, `split-2`, `form`) and the page patterns (`sections`, `spotlight`, `link-card`). A project stylesheet may add spacing or placement on top of system classes, never a second look for a button, card, chip, switch, tab, field, list or dialog.
4. **Only when nothing fits, add a component to the system**, not to the page: CSS in `css/components.css` (tokens only, light and dark), behavior in `js/lds.js` behind a `data-lds-*` attribute (and a binding in `react/index.tsx` if React must own its state), a spec in `docs/spec/<slug>.mjs`, then `node scripts/build-docs.mjs`. The build checks icons, classes and links.

**Composing a whole screen?** Start from `docs/examples/`: `landing.html` (marketing page), `dashboard/` (a 33-page admin app on one app shell, from `src/dashboard/` via `npm run build:examples`) and `mobile.html` (phone app screens). They are built only from the components below and show how they combine.

Signs you are about to duplicate a component: a new class that sets `border-radius`, `background` and `padding` on something clickable; a hand-made toggle, tab bar, ring, segmented control or dropdown; a `box-shadow` on resting content; a raw hex color or pixel spacing outside the 4 px grid.

## Conventions every component follows

- The page (or subtree) root carries `class="lds"` for the base type, colors and resets. Theme with `data-theme="light|dark|system"`.
- Classes are BEM-like: `.block`, `.block__part`, `.block--variant`. State uses ARIA where it exists (`aria-pressed`, `aria-selected`, `aria-expanded`, `aria-current`, `aria-checked`, `aria-invalid`) and `is-*` classes otherwise (`is-open`, `is-loading`, `is-invalid`, `is-done`, `is-closing`).
- Behavior marked **JS** comes from `js/lds.js`: `init()` wires every `data-lds-*` element (call it again after rendering new markup). In React, use `react/index.tsx`; it renders the same markup and owns the state.
- Motion lives in CSS on the motion tokens: enter on a spring, leave faster on `--ease-exit`, transitions for anything reversible, `prefers-reduced-motion` respected. See the Motion group.
- Icons are `<span class="ic" aria-hidden="true">name</span>` with names from `icons/icons.json` only; an unknown name renders blank.
- Copy: sentence case, buttons named for their outcome, no em dashes, errors say what happened and what to do.
