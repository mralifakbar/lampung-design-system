Form layout

The frame every form uses: form stacks fields 20 px apart, form__row puts short fields side by side when there is room, and form__actions ends the form with its buttons. Fields inside are always .field.

Usage

Use it when

  • Any form with more than one field: sign up, profile, checkout, a course settings page, the body of a dialog or sheet.
  • Two or three short fields belong together on one line on wide screens (first and last name, city and postal code, start and end date) and must stack on phones.
  • A form needs its buttons at the end, primary on the right on wide screens and full width on top on phones.

Use something else when

  • Placing anything that is not a form (cards, badges, toolbars): use Layout primitives.
  • The single field itself: label, control, helper and error: use Text field.
  • One search box above a list: use Search field. A search field is not a form; it filters as you type and has no submit row.
  • A setting that applies the moment it changes: use Switch. Settings lists save per row; they do not get a form__actions row.
  • Long values read back as label and value, not edited: use Key-value.

Where it goes. Inside the page content column (cap it with measure or a max width around 560 px for single-column forms), inside a dialog, modal or sheet body, or in the main column of split-2. On phones the form is full width with the 20 px page gutter.

Examples

Anatomy

PartWhat it is
form.formRequired. The <form> element. A flex column with 20 px between children.
.fieldRequired for each input: .field__label + .control (or another input component) + optional .field__help. See text field.
.form__rowOptional. Grid of equal columns, each at least 200 px; drops to one column when there is no room. 16 px gap.
fieldsetOptional. Groups related fields with a <legend>; the system resets its border and padding.
.form__actionsRequired when the form submits. Buttons aligned to the end with 10 px between; below 560 px they stack, full width, primary on top.

States

StateHow
errorPer field: .control.is-invalid + aria-invalid="true" + .field__help--error with an error icon. Validate after the first blur, then live.
submittingThe primary button gets .is-loading and aria-busy="true" (setLoading(btn, true)); the fields stay editable.
many errorsPut an alert above the form that lists them with links to each field, then focus the alert.

Motion and microinteractions

  • The form itself never animates. Fields that appear on a choice (an "Other" text box) open with height expand on --spring-smooth over --d-smooth.
  • Errors change color in --d-fast on --ease-standard; the helper line keeps its height so nothing jumps. A refused submit may shake the first invalid field once.
  • Under reduced motion the expand becomes a 120 ms cross-fade.

Accessibility

  • Use a real <form> so Enter submits and the browser can autofill; the submit button is type="submit", the others type="button".
  • Every input has a <label for>; helper and error text are linked with aria-describedby.
  • Groups of checkboxes or radios go in a <fieldset> with a <legend>.
  • Source order is visual order: cancel before submit in the markup. On phones column-reverse shows the primary on top while Tab still reaches Cancel first, which matches reading the buttons from the end of the form.
  • On a failed submit move focus to the first invalid field or to the summary alert.

Do and don't

check_circleDo

  • Cap single-column forms near 560 px; long inputs across a wide screen are hard to scan.
  • Pair only short, related fields in a form__row; keep one idea per row.
  • Name the primary for its outcome ("Save profile", "Schedule exam").

cancelDon't

  • Lay out fields with auto-grid or hand-written flex; error lines and labels stop lining up.
  • Put three or more unrelated fields in one row to save space.
  • Add a second primary to form__actions, or put the actions above the fields.

Behavior and code

Plain HTML. None needed for layout. setLoading(button, true) for the submitting state; shake(el) for a refused submit.
